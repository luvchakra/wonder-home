# Internationalization — implementation map

The spec (`WonderHome_Master_Internationalization_Localization_MultiCurrency.md`, 2026-09-24) asks for a short map of what already exists before any code. This is that map, and the integration decision taken for each point. The stories are module 22 in `backlogs/22-Internationalization-and-Localization.md`.

| Area | What exists (2026-09-24) | Decision |
|---|---|---|
| **i18n library** | None. Every UI string is hard-coded English. | Add our own small catalog: `packages/core/src/i18n/messages/<lang>.ts` with stable keys and a `t()` that has fallback, interpolation and plurals. This avoids adding a runtime dependency for server-rendered strings. Every catalog is complete for the keys it ships, and a unit test holds it to that. |
| **Existing onboarding** | `household_onboarding` is household-level, Admin-only and twelve screens (story 02-009). There is no per-person setup state. | Localization is personal, so its state lives on the person (`household_members.locale_setup_*`), never in a second household wizard. It runs after family setup ("Go to my home" leads into it) and reuses the same `OnboardingFrame`. Anyone who skips it gets one dismissible Home card. |
| **Settings** | `/settings` has sections of `IconTile` rows with sub-pages at `/settings/<name>`. The time zone is shown read-only. | Add a "Language & Region" row, with `/settings/language-region` plus picker sub-pages (language, region, currency, date & time, member languages). There is no new top-level navigation item. |
| **Preference storage** | `households.timezone` exists and is not editable. `profiles.timezone` is never read. `household_voice_settings.language` is the voice recognition language only. | **Household** (Admin writes, `households_update_admin`): `region`, `currency`, `measurement_system`, `default_language`, and the now-editable `timezone`. **Person** (self or Admin, existing member policies): `language`, `date_format`, `time_format`, `measurement_system`. Voice recognition language stays separate: language is independent of the voice provider (spec §J). |
| **Formatting** | 35 hard-coded `en-GB`/`en-US`/`en-CA`/`en-IN` calls. `session.ts` date/time helpers. Two `₹`-building money formatters. | One formatter (`i18n/format.ts`, Intl-only, Latin digits). A request-scoped locale (`i18n/request.ts`, React `cache`) is set once by `requireSession`, so the existing helpers become locale-aware without touching every call site. Outside a request (tests, jobs) the defaults apply, which is today's behaviour. |
| **Currency** | Money records carry their own `currency`. Households have none. Bills and Groceries guess "INR". | `households.currency` is the default for new records only. Existing records keep their own. Nothing is ever converted. |
| **HomeTalk** | No reply-language concept. Deterministic replies are in English. The HomeBrain validator is English-only. | PR 2 (story 22-005): a language line in `systemFor` and in the answer briefing, understanding into the same language-neutral intents, and the same gates. |
| **Notifications** | Final English strings in `title`/`body`. | PR 2 (story 22-006): structured event + params, rendered per recipient. |
| **`<html lang>`/`dir`** | Static `lang="en"`, no `dir`. | The shell (`DocumentLocale`) sets `lang`/`dir` on the document from the viewer's language. The root layout stays static, because reading a cookie there would make every page dynamic, the landing and legal pages included. |

**Invariant (spec §47).** Localization changes how WonderHome speaks. It never changes what is stored, who someone is, what they may do, or what a record's currency is.
