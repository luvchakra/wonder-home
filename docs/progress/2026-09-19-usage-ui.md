# Usage this period, in Settings (story 20-005)

**Date:** 2026-09-19
**Scope:** `packages/core/src/billing/{entitlements,repository}.ts`, `apps/web/app/settings/page.tsx`, `apps/web/app/api/v1/households/[householdId]/entitlements/route.ts`
**Status:** Done

## What was missing

Modules 20-001 through 20-004 built the whole entitlement service — plan
features, atomic usage counters, upgrade/downgrade with a re-derived
preview — but nothing showed a household what it had actually used.
Settings rendered the plan and a plan-switcher (`PlanForm`, story 20-004);
`/api/v1/households/{householdId}/entitlements` (story 20-002) returned the
plan's limits, never what had been spent against them. A household on Free
with 47 of 50 agent runs left this month had no way to find that out.

## What was built

`usageSummary` (`billing/repository.ts`) reads the same counters `consume`
increments and `may` checks — `usedThisPeriod`, per enabled feature — so the
number a household sees is the number their quota is actually enforced
against, not a second copy that could drift. An unmetered feature
(`limitPerPeriod: null`) gets `used: null`: "unlimited" has nothing to be
"used of."

The `/entitlements` route now returns this instead of the older
limits-only shape — additive, not breaking (existing fields unchanged,
`used` is new per feature). Nothing in the app actually called that REST
route, though; Settings is a server component that reads the repository
directly, matching how it already reads `loadSubscription`/`listPlans`. So
Settings gained a "Usage this period" section (`MetricGrid`, the same
component Home's dashboard metrics use), shown above the plan-switcher and
only for features that are actually metered — an empty list produces no
section at all, rather than a heading over nothing.

`describe()` (the feature-key → label lookup `featureSummary` already used
privately) is now exported, so `usageSummary` labels usage exactly the way
`featureSummary` already labels limits, with no second copy of the
`FEATURES` lookup.

## What was verified — and what wasn't, and why

- `npm run typecheck`, `lint`, `npm run security` (9/9), `npm run build` —
  clean; the new route shape appears in the build's route manifest
- `npx playwright test --project=desktop` — 126/126, including
  `e2e/domains.spec.ts`'s dynamic OpenAPI/route cross-check against the
  updated `/entitlements` doc
- `node --test scripts/test-entitlements-rls.mjs` — 13/13, unaffected
  (`usageSummary` reads the same tables/RLS this suite already covers)

**No new unit test for `usageSummary` itself**, deliberately, matching this
file's own established split: pure functions (`assessPlanChange`,
`checkEntitlement`, `featureSummary`) get `vitest` unit tests;
`SupabaseClient`-composing functions in this same file
(`previewPlanChange`, `changePlan`) do not — they are thin joins of
already-tested primitives, verified by typecheck and the DB/RLS suite that
covers what they read. `usageSummary` is the same shape of function
(`loadSubscription` + a loop over `usedThisPeriod`, both already exercised
by `test-entitlements-rls.mjs`), so it follows the same convention rather
than introducing a one-off mocked-`SupabaseClient` test for this function
alone.

**Not driven in a live browser.** This session has no local Supabase
stack (PostgREST + auth) to sign in as a real household and see numbers
render — the same limitation noted in this session's PR reviews of prior
UI stories. The rendering path (`MetricGrid` with a `label`/`value` pair)
is the same component and prop shape Home's dashboard already uses in
production, so the risk here is in the data (`usageSummary`'s query logic,
covered as above), not in an unfamiliar rendering path.
